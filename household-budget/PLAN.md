## 1. 제품 초안

### 1.1 목표
흩어진 카드·계좌·보험·통신·대출·구독을 **한 화면에서 자동으로** 보고, 고정비와 변동비를 나눠 예산을 관리한다.

### 1.2 핵심 화면 (프로토타입에 구현됨)

| 화면 | 기능 |
|---|---|
| 대시보드 | 이번 달 지출/수입/예산 잔여, 카테고리별 지출, 일별 누적 지출 그래프, 다가오는 고정 납부, 순자산(자산−부채) |
| 거래내역 | 전체 내역, 출처(연동 방식)·카테고리 필터, 카테고리 수정 → "이 가맹점은 항상 이 카테고리" 규칙 자동 생성, 수기 입력 |
| 고정지출 | 보험료·통신비·구독·관리비·대출이자 등 반복 납부 목록, 납부일, 연간 합계, 실제 출금 내역과 자동 매칭 |
| 가져오기 | 카드사/은행 CSV 업로드, 카드 승인 문자(SMS)/푸시 알림 붙여넣기 → 자동 파싱 |
| 연동 관리 | 기관별 연동 방식·상태·마지막 동기화 시각, 재인증 필요 알림 |
| 연동 가이드 | 아래 2~4장 요약 |

### 1.3 데이터 모델 (최소)

```
Institution   { id, name, type: bank|card|insurance|telecom|loan|pension, method, status, lastSyncAt, consentExpiresAt }
Account       { id, institutionId, name, kind: asset|liability, balance, maskedNo }
Transaction   { id, accountId, postedAt, amount(+입금/-지출), merchant, rawText, category, source, status: approved|canceled|settled, externalId, dedupKey }
Recurring     { id, name, amount, dayOfMonth, category, accountId, matchKeyword }
Rule          { pattern(가맹점 키워드), category }
Budget        { month, category, limit }
```

- `dedupKey = 날짜 + 금액 + 정규화된 가맹점 + 카드 끝4자리` — 문자/CSV/API가 같은 거래를 중복으로 넣는 것을 막는 핵심.
- 카드 거래는 **승인 → (취소) → 매입/청구** 상태를 갖는다. 승인 기준으로 보여주고, 취소는 원거래와 상계.

### 1.4 단계별 로드맵

| 단계 | 기간(예상) | 내용 |
|---|---|---|
| MVP | 2~3주 | 수기 입력 + CSV 가져오기 + 문자 파싱 + 자동 분류 규칙 + 고정지출 (= 현재 프로토타입 범위) |
| v1 | +3~4주 | 스크래핑 API(CODEF 등) 연동으로 카드·계좌·보험 자동 수집, 서버 + DB, 매일 자동 동기화 |
| v2 | 이후 | 모바일 앱(알림 수신 자동 기록), 예산 초과 알림, 월말 리포트, 가족 공유 |
| 서비스화 | 별도 판단 | 다른 사람에게 제공하려면 마이데이터 사업자 제휴 필수 (3.3 참고) |

## 2. 결론 먼저: 무엇이 실현 가능한가

**"나 혼자 쓰는 가계부"인지, "남에게 제공하는 서비스"인지에 따라 답이 완전히 다릅니다.**

| 방식 | 개인이 직접 사용 | 남에게 서비스 | 커버 범위 | 자동화 | 난이도/비용 |
|---|---|---|---|---|---|
| **A. 마이데이터 API 직접** | ✕ (금융위 허가 사업자만) | 허가 필요 | 은행·카드·보험·증권·대출·통신 일부 | 완전 자동 | 매우 높음 |
| **B. 마이데이터 사업자 제휴/연동** | △ (기업 대상 계약) | ○ | 위와 동일 | 완전 자동 | 높음 |
| **C. 오픈뱅킹 (금융결제원)** | ✕ (이용기관 자격 필요) | ○ 핀테크 기업 | 은행 계좌·잔액·거래내역 (카드 미포함) | 자동 | 높음 |
| **D. 스크래핑 중개 API (CODEF·쿠콘·하이픈 등)** | ○ (데모/개발 계정 → 정식은 계약) | 제약 있음, 법률 검토 필요 | 은행·카드·보험·통신사·국세청·건보 등 매우 넓음 | 자동 (주기적 재인증) | 중간, 건당/월 과금 |
| **E. 카드사·은행 엑셀/CSV 내보내기** | ○ | — | 모든 금융사 | 수동 (월 1회) | 낮음, 무료 |
| **F. 문자/푸시 알림 파싱** | ○ | ○ (앱 내 기능) | 알림 오는 카드·계좌 | 실시간 자동 | 낮음 |
| **G. 기존 자산관리 앱 내보내기** (예: 뱅크샐러드 엑셀 내보내기) | ○ | — | 그 앱이 연동한 전부 | 수동 | 매우 낮음 (기능 제공 여부 확인 필요) |
| **H. 이메일 청구서 파싱** | ○ | ○ | 통신비·보험·카드 명세서 | 자동 (메일 수신 시) | 중간 |

### 추천 조합 (개인용)

1. **즉시 (MVP):** E + F + 수기 고정지출
   - 카드 승인 문자/알림 → 실시간 자동 기록 (변동비 대부분)
   - 월 1회 카드·은행 CSV 업로드 → 누락분 보정·정산
   - 보험료·통신비는 고정지출로 등록 → 실제 출금과 자동 매칭
2. **자동화 (v1):** D (스크래핑 API) 추가 → 매일 새벽 자동 수집, 문자는 실시간 보조로 유지
3. **팁:** 결제 채널을 줄이면 연동이 쉬워진다. 보험·통신·구독·관리비를 **주력 카드 1~2장 + 주거래 계좌 1개**로 자동이체를 모으면, 카드+계좌 2개 채널만 연동해도 지출의 대부분이 잡힌다.

## 3. 연동 방식별 상세

### 3.1 지출 유형별 수집 경로

| 항목 | 1순위 경로 | 보조 경로 | 비고 |
|---|---|---|---|
| 신용/체크카드 | 승인 문자·푸시 (실시간) | 카드사 이용내역 CSV, 스크래핑 API | 할부·해외결제·취소 처리 필요 |
| 은행 계좌 | 스크래핑 API (거래내역) | 입출금 알림, 인터넷뱅킹 엑셀 | 자동이체(보험·통신·관리비)가 여기서 잡힘 |
| 보험료 | 카드/계좌 자동이체 내역 | 보험 계약정보: 마이데이터·스크래핑, 신용정보원 '내보험다보여' 조회 | 계약 목록(만기·보장)은 별도 수집 |
| 통신비 | 카드/계좌 자동이체 내역 | 통신사 이메일 청구서, 통신사 스크래핑 | 통신 분야 개인정보 전송요구권(마이데이터) 확대 진행 중 — 시행 범위 확인 필요 |
| 대출 | 스크래핑 API (잔액·이자) | 계좌 출금 내역 | 부채로 순자산 계산 |
| 연금·보장성 | 금감원 통합연금포털 조회 (수동) | 스크래핑 | 분기 1회 업데이트면 충분 |
| 구독(OTT 등) | 카드 내역에서 반복 결제 자동 탐지 | — | 같은 가맹점·비슷한 금액이 매달 반복되면 '고정지출 후보'로 제안 |
| 현금 | 수기 입력 | ATM 출금 내역 | |

### 3.2 스크래핑 중개 API (방식 D) 연동 흐름

```
[앱] 기관 선택 → 간편인증(카카오/PASS/네이버 등) 또는 공동·금융인증서 요청
   → [내 서버] 중개 API에 "계정 등록(connectedId 발급)" 요청
   → [사용자 휴대폰] 간편인증 승인
   → [내 서버] connectedId 저장 (아이디/비밀번호/인증서 원본은 저장하지 않음)
   → [스케줄러] 매일 새벽: connectedId로 카드 승인내역·계좌 거래내역·보험 계약 조회
   → 정규화 → 중복제거 → 자동 분류 → DB 저장 → 앱 알림
```

- 대표 업체: CODEF(헥토데이터), 쿠콘, 하이픈 등. 개발자용 데모/샌드박스는 비교적 쉽게 열리고, 정식 운영은 사업자 계약·과금 구조인 경우가 많다 (**요금·개인 가입 가능 여부 확인 필요**).
- 현재 저장소의 Netlify Functions 구조를 그대로 활용 가능: `netlify/functions/sync-*.js` + Netlify Scheduled Functions로 일 1회 동기화.
- 주의: 금융사 화면 개편 시 일시 장애가 날 수 있음 → 실패 감지·재시도·알림 필수.

### 3.3 마이데이터 / 오픈뱅킹 (방식 A·B·C) — 서비스화할 때

- **마이데이터(본인신용정보관리업):** 2022년 1월부터 표준 API 방식으로 전면 시행. 금융위원회 허가가 필요하고(자본금·보안·인력 요건), 허가 사업자는 스크래핑 사용이 제한된다. 개인 개발자가 직접 붙는 것은 불가.
- **오픈뱅킹:** 금융결제원 이용기관 자격 필요. 은행 계좌 위주이고 카드 내역은 범위가 다르다.
- **비금융 마이데이터:** 개인정보보호법 개정으로 개인정보 전송요구권이 생겼고, 의료·통신·에너지 등 분야부터 단계적으로 확대 중 (**시행 일정·범위 확인 필요**).
- **현실적인 서비스화 경로:** 이미 허가받은 마이데이터 사업자 또는 금융 데이터 플랫폼과 B2B 제휴해 데이터를 받는다. 법률 검토(개인정보·신용정보법)와 보안 인증(ISMS 등) 비용을 사업계획에 포함해야 한다.

### 3.4 문자·알림 파싱 (방식 F) 플랫폼별 현실

| 플랫폼 | 방법 | 제약 |
|---|---|---|
| Android | `NotificationListenerService`로 카드/은행 앱 푸시 수신, 또는 SMS 수신 | Play 스토어 배포 시 SMS 권한은 기본 문자앱 등만 허용 → **알림 리스너 방식 권장**. 개인용 직접 설치(APK)는 제약 적음 |
| iOS | 문자 접근 불가. **단축어(Shortcuts) 자동화** "특정 문자 수신 시" → 내 서버 웹훅으로 본문 전송 | 자동화 실행 설정 필요, 푸시 알림 내용은 읽을 수 없음 |
| 공통 | 프로토타입처럼 문자 내용을 복사해 붙여넣기 | 수동 |

파서는 카드사별 문구 패턴(승인/취소/일시불/할부/누적, 입금/출금)을 정규식으로 처리하고, 인식 실패 문구는 "검토 필요"로 남긴다.

## 4. 운영 프로세스

### 4.1 전체 데이터 흐름

```
수집(Collect)          정규화(Normalize)         정제(Clean)              분류(Classify)          활용(Use)
───────────────       ─────────────────       ─────────────────       ─────────────────      ────────────
스크래핑 API (일 1회)  →  공통 Transaction 스키마  →  중복 제거(dedupKey)    →  사용자 규칙            →  대시보드/예산
문자·푸시 (실시간)     →  금액 부호·날짜·KST 통일  →  승인↔취소 상계          →  키워드 사전            →  고정지출 매칭
CSV (월 1회)          →  가맹점명 정규화          →  계좌이체 ↔ 카드대금    →  (선택) LLM 분류        →  월말 리포트
수기 입력                                         내부이체 제외                  미분류 → 검토함          →  알림
```

### 4.2 주기별 운영 체크리스트

| 주기 | 자동/수동 | 작업 |
|---|---|---|
| 실시간 | 자동 | 승인 알림 수신 → 기록 → 예산 80%/100% 초과 시 알림 |
| 매일 새벽 | 자동 | 스크래핑 API로 전일 내역 수집 → 문자 기록과 대조해 누락·중복 정리 → 실패 기관 알림 |
| 매주 | 수동 5분 | '검토 필요'(미분류·파싱 실패) 정리, 새 규칙 확정 |
| 매월 초 | 반자동 | 카드 청구서 금액 vs 앱 집계 대조(정산), 고정지출 미납/금액 변동 확인, 월 리포트 |
| 분기 | 수동 | 보험·연금·대출 잔액 업데이트, 구독 정리 제안 확인 |
| 연 1회 | 수동 | 인증서 갱신, 연동 동의 재동의(마이데이터 전송요구는 유효기간 있음), 연말정산용 카테고리 합계 추출 |

### 4.3 반드시 처리해야 하는 데이터 이슈

1. **이중 계상:** 카드로 쓰고 → 계좌에서 카드대금이 빠지면 두 번 잡힘 → 계좌의 "○○카드 결제대금" 출금은 **지출이 아닌 이체**로 분류.
2. **내 계좌 간 이체:** 본인 계좌끼리 이동은 수입/지출에서 제외.
3. **취소·부분취소:** 원거래와 금액·가맹점·카드로 매칭해 상계.
4. **할부:** 승인 시 전액 vs 월 청구액 중 표시 기준 선택 (기본: 승인 시 전액, 옵션으로 월할).
5. **해외결제:** 승인 시 외화, 매입 시 원화 확정 → 매입 금액으로 갱신.
6. **소스 간 중복:** 문자 + API + CSV가 같은 거래를 가져옴 → dedupKey + ±1일·동일금액 매칭.

### 4.4 보안 원칙

- 금융사 아이디·비밀번호·인증서 원본은 **저장하지 않는다** (간편인증 + connectedId/토큰만 보관).
- 토큰·API 키는 서버 환경변수/비밀 저장소에만, DB에는 암호화(AES-256)해서 저장.
- 개인용이면 데이터는 본인 DB(예: Supabase/개인 서버/로컬)만 사용, 외부 분석 도구로 원문 전송 금지.
- 계좌번호·카드번호는 마스킹(끝 4자리)만 보관.
- 앱 잠금(생체인증), 세션 만료, 접근 로그.

### 4.5 장애 대응

| 상황 | 감지 | 대응 |
|---|---|---|
| 스크래핑 실패 (금융사 점검·화면 변경) | 동기화 결과 코드 | 3회 재시도 → 실패 시 알림, 문자 기록으로 임시 보완 |

| 금액 불일치 (월말 정산) | 청구서 vs 집계 차이 | 차이 내역 리스트업 → 누락 거래 수기 보정 |

## 5. 기술 스택 제안 (개인용 기준)

- **프론트:** 현재 프로토타입(HTML/JS) → React/Next.js 또는 모바일은 React Native/Flutter (알림 리스너가 필요하면 Android 네이티브 모듈)
- **백엔드:** Netlify Functions(이 저장소와 동일) 또는 Supabase Edge Functions, 스케줄러로 일 1회 동기화
- **DB:** Supabase(Postgres) 또는 SQLite. 행 단위 보안(RLS) 적용
- **수집:** 스크래핑 API SDK, iOS 단축어 → 웹훅 엔드포인트(`/api/ingest/sms`)
- **분류:** 규칙 엔진(키워드 → 카테고리) 우선, 미분류만 LLM 보조 분류 (선택)
